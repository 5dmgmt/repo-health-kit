# AI で作ったアプリのデータの守りを点検する

毎朝の機械的な点検と、人がコードや本番を見て確かめる点検を組み合わせます。静的な結果は「migration の記述上は〜（本番は未確認）」です。SQL Editor で直接当てた変更や、複雑な動的 SQL までは追い切れません。

## 自動の点検

`bin/data-guard.py` は全リポをまとめて1回読みます。共有する Supabase プロジェクトでは、別アプリの利用者にも同じ認証基盤が使われるため、ログインだけを条件にした方針を FAIL に上げます。ref は `supabase/.temp/project-ref`、公開 URL の順に見つけ（`project-ref` が見つかれば公開 URL は読みません）、表示は先頭4字にします。`.claude`（Claude Code の作業フォルダ・worktree）、直下に `.git` を持つ入れ子の checkout（git worktree・サブモジュールを含む）、`.vercel`・`.turbo` は本流ではないので読みません。`dist`・`build`・`out`・`coverage` も、親のフォルダに `package.json` があるとき（リポの根・monorepo の各パッケージの根）だけ、ビルドの出力として読みません。`app/api/build/` や `lib/out/` のようなソースのフォルダは読みます。

静的 SQL は `supabase/migrations`・`supabase/schemas` と、それ以外の SQL の関連する DDL を読みます。ファイル名順に CREATE・ALTER・DROP、RLS の有効・無効、方針の変更、表の改名を追います。共有 ref のリポはまとめて追いますが、別リポ間の本番への適用順は確定できません。同じファイル名の変更はパス順で照合するため、本番の目録と合わせて確認してください。

RLS が有効で方針0本の表は全拒否として扱います。INSERT は `with check`、ALL の省略された `with check` は `using` を見る形です。`service_role` だけに向けた無条件の方針は指摘しません。動的 SQL の RLS 有効化らしい記述があれば、その共有グループの RLS 不明を NOTE に下げます。実行された表を特定できないため、本番の確認が必要です。

ブラウザ側の変数名、client component からの1段の import、手元の `.next/static` を見ます。`server-only` の import はビルドの保護として扱います。git 履歴では鍵ファイルの名前だけを調べ、初回は全履歴、以後は前回の ref から追加された履歴を読みます。`.env.example`・`.env.sample`・`.env.tpl` は履歴の名前の照合から除外します。値の検査の代わりにはなりません。履歴に残る指摘は鍵の入れ替えを確かめるまで続きます。

API は cron の秘密の確認、captcha の未設定時の許可、Map による連射制限、認証の語が見当たらない入口を見ます。初回の入口一覧は INFO、次回から増えた入口は WARN です。認証を含む proxy / middleware の接頭辞検査・単純な matcher がある入口は除きます。複雑な正規表現、共通ヘルパー、外部認証の実効性は人が確認します。テナント列と方針の照合も、所属の確認が正しいことを保証しません。

`gh` がありログイン済みなら、公開設定と Dependabot の未対応件数を取得し24時間使います。公開への変更は WARN、公開リポの SQL の当たり・鍵ファイル履歴は FAIL です。`RH_DATA_GITHUB=0` でこの通信を止められます。

## 利用者が設定したときの実測

- `RH_SUPABASE_CATALOG=1`: [監査専用の役割](supabase-audit-role.md)で本番の目録を読みます。アプリの行は読みません。
- `RH_SUPABASE_ANON_PROBE=1`: 手元の `.env*` の公開 URL と `NEXT_PUBLIC_SUPABASE_ANON_KEY` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` だけを読みます。SQL・目録で分かった表ごとに GET 1回、1秒以上あけて直列に取得し、本文を破棄します。1表1日1回です。初回は読める表を WARN、次の日以降は増えた表を FAIL にします。0件では拒否と空の表を区別できません。公開鍵が見つからなければ未検査です。
- `RH_SITE_URLS='https://example.invalid'`: 1サイト1日1回、トップの HTML と同じホストの JS、ソースマップ、秘密ファイルのパス、ヘッダーを見ます。各取得は10秒上限で、1秒以上あけます。別ホスト・ログイン後の JS は未検査です。redirect は追いません。`/.env`・`/.git/config` の404以外は FAIL なので、全パスへ HTML を返すサイトでは誤検知することがあります。

公開鍵・接続文字列は curl / psql の引数に出しません。結果と状態には行データ、秘密の値、定義本文を保存しません。

## 据え置きと所有アプリ

`~/.config/repo-health-kit/data-allow.tsv` に、種類・対象・ハッシュ（空欄可）・期限・理由・所有アプリ（省略可）をタブで区切って書きます。`RH_DATA_ALLOW` でパスを変えられます。[書式見本](../config/data-allow.example.tsv)を参照してください。

対象は `public.app_a_profiles`、`public.app_a_profiles:app_a_access`、関数名、または `app-a:app/api/status/route.ts` の形です。公開への変更は種類 `repo_public`、対象 `app-a:-` で据え置けます。定義がある指摘には md5 の先頭12字が出ます。その値をハッシュ欄へ書くと定義が変わったときに据え置きが効かなくなります。期限は必須で最長180日です。残り7日以内は予告します。理由は記録用で、点検レポートには転載しません。

SQL の対象文の直前には `-- rh-allow: 公開一覧として確認 until YYYY-MM-DD` と書けます。期限と理由の条件は同じです。RLS 無効の `rls_off` と、ブラウザ側の service_role・秘密鍵の指摘は据え置けません。一般の `allow.tsv` ではデータの点検を据え置けません。

`RH_SUPABASE_APPS` に所有アプリの TSV のパスを設定すると、台帳にない表を WARN にします。列は接頭辞または表名・アプリ名・備考です。末尾 `_` または `*` を接頭辞として扱い、それ以外は表名と一致させます。[見本](../config/supabase-apps.example.tsv)は架空の名前です。

## 人が確認する5つの範囲

1. **ログインと認可を分けて読む**: URL・ボディの id / token / email / orgId を、そのまま条件にしていないか確認します。service_role の入口に本人・所有者の確認があるか、認証なしの DB 操作、送られた金額・権限・スコアの採用、共有リンク・招待の期限・回数・失効、秘密のデータを client component に静的 import していないかを読みます。
2. **テナント境界のコードを読む**: service_role の問い合わせが所属先で絞られるか、別組織の id に置き換えても所有者チェックが働くか、共通関数まで追います。列名の有無だけで合格にしません。
3. **ログイン済みの道具で設定を確認する**: 人が見ている場で認証プロバイダ、`supabase db advisors`、Vercel の環境変数の名前を確認します。共有プロジェクトでは登録の入口も共有です。変更前に既存の利用者への影響を確かめます。秘密の値は表示しません。
4. **テスト用の2アカウントで確認する**: 利用者が用意したアカウント A で、B のデータの URL を開いて認可を確かめます。共有プロジェクトでは別アプリ同士でも確認します。ログイン後の配信物も調べ、保護対象の実際の本文が入っていないか確認します。プロパティ名だけでは判定しません。
5. **記録と別の視点で確認する**: アクセス記録が実際に残るか、重大度と未確認分を分けて読みます。別のレビュアーや Claude Security の深層スキャンも使い、機械の指摘を根拠と照合します。

確認できなかった範囲を最後に書きます。直すときは対象と影響を利用者と確認し、鍵の入れ替えや本番の設定変更を自動点検の中で行いません。
